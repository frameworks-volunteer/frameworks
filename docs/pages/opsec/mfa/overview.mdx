# Multi-Factor Authentication (MFA / 2FA)

<TagList tags={frontmatter.tags} />
<AttributionList contributors={frontmatter.contributors} />

## Summary

> 🔐 **Key takeaway:** MFA only helps when method strength, recovery controls, and incident response are designed together.
> For critical accounts, default to phishing-resistant authentication: **FIDO2/passkeys/security keys > TOTP > push > SMS**.

This framework centralizes guidance that often appears scattered across platform-specific pages (Discord, Telegram,
X/Twitter, Google, travel OPSEC, and SIM-swap defense). Use this as your baseline policy, then adapt per platform.

## Why this matters

Account takeover remains one of the highest-impact and most common attack paths in Web3 operations. MFA reduces risk,
but only when implemented as an **operational system**, not a one-time setting:

- weak factors (especially SMS) can still be hijacked
- recovery flows can silently bypass strong MFA
- partial rollout (admins only, no comms/ops accounts) leaves critical gaps
- untested break-glass access can fail during incidents

## Method hierarchy (default policy)

Use the strongest factor each platform supports:

1. **FIDO2 / passkeys / security keys** (WebAuthn, hardware-backed) — default for critical accounts
2. **TOTP** (authenticator app or hardware token) — acceptable fallback where FIDO2 is unavailable
3. **Push MFA** — acceptable only with number matching and anti-fatigue controls
4. **SMS/voice OTP** — emergency fallback only; avoid for critical systems

### Enforcement by account tier

- **Tier 0 (critical):** treasury, multisig signers, exchange admins, DNS/registrar, identity provider, production cloud
  control plane
  - must use FIDO2/security keys when supported
  - SMS prohibited unless platform is SMS-only (requires documented exception)
- **Tier 1 (high):** comms/admin accounts, CI/CD maintainers, GitHub org admins
  - FIDO2 preferred, TOTP allowed
  - push allowed only with anti-fatigue settings
- **Tier 2 (standard):** lower-impact internal tools
  - at minimum TOTP
  - SMS discouraged and tracked as technical debt

### Baseline rules

- Disable SMS/voice MFA whenever a stronger method exists
- Enroll at least **two factors** for every critical account (primary + backup)
- Store recovery codes offline in controlled storage (not only cloud notes)
- Protect password manager and account-recovery email with strong MFA
- Separate where possible: password storage, OTP generation, and high-risk admin sessions

## Operational failure modes and mitigations

### 1) SIM swap / phone-number takeover

**Failure mode:** attacker ports a number, intercepts SMS OTP and account reset flows.

**Mitigations:**

- do not rely on SMS for critical accounts
- remove recovery phone numbers where not required
- enable carrier-level port-out PIN and no-port flags
- protect email and IdP accounts with FIDO2 (to prevent reset-chain compromise)

**Response trigger:** unexpected carrier loss of service, new-device alerts, or password-reset emails.

### 2) MFA fatigue (push bombing)

**Failure mode:** repeated push prompts pressure users into accidental approval.

**Mitigations:**

- require number matching / challenge codes for push MFA
- disable "approve/deny"-only prompts where possible
- train staff to treat unsolicited prompts as incidents
- throttle/lock accounts after repeated prompt abuse

**Response trigger:** repeated MFA prompts without user action.

### 3) TOTP seed theft / secret extraction

**Failure mode:** attacker steals OTP seed (QR/export/backup), then generates valid codes.

**Mitigations:**

- enroll TOTP only on hardened dedicated devices
- disallow screenshots or cloud sync of seed QR/secrets
- avoid storing signer seed phrases and OTP seeds on the same device/account
- rotate TOTP secrets after suspected malware or device compromise

**Response trigger:** unexplained successful MFA logins from unfamiliar devices/IPs.

### 4) Shared devices / role accounts

**Failure mode:** one enrolled factor is shared across multiple people, removing accountability and revocation clarity.

**Mitigations:**

- no shared authenticator apps for critical accounts
- map every enrolled factor to an individual person and asset ID
- use delegated access or role-based admin controls instead of credential sharing
- review factor ownership quarterly

**Response trigger:** inability to identify which person approved a login or factor change.

### 5) Lost, stolen, or unavailable phone/key

**Failure mode:** legitimate operator is locked out, or attacker uses stolen backup artifacts.

**Mitigations:**

- maintain at least one independent backup factor per critical account
- store backup codes in offline controlled vaults
- test recovery paths in drills (not only in theory)
- rotate all factors immediately after confirmed loss/theft

**Response trigger:** user lockout during incident response or travel.

## Organizational process requirements

### Enrollment standard

- identity-verify each person before enrolling factors
- enroll factors during controlled onboarding sessions
- record factor type, owner, device ID, and recovery location
- enforce minimum methods by tier (no ad hoc per-user choices)

### Backup and recovery standard

- define who can approve recovery and under what evidence
- require dual control for critical recovery actions
- maintain offline recovery artifacts with documented access controls
- test recovery at least quarterly and after major platform changes

### Offboarding standard (joiner/mover/leaver)

- revoke all factors and active sessions immediately when roles change
- remove old devices and stale backup factors
- rotate recovery codes after privileged departures
- validate ownership for service/admin accounts after offboarding

### Break-glass access

- keep dedicated emergency accounts with stronger-than-normal controls
- store credentials and recovery factors in sealed, logged, access-controlled workflows
- require post-incident credential/factor rotation after any break-glass use
- alert security leadership on every break-glass event

### Incident response when MFA is compromised

When compromise is suspected or confirmed:

1. **Contain:** revoke active sessions, freeze sensitive actions, lock impacted accounts
2. **Recover control:** reset passwords, rotate/re-enroll all MFA factors, invalidate recovery codes
3. **Scope impact:** review audit logs (factor changes, device enrollments, password resets)
4. **Protect adjacent systems:** rotate API keys/tokens, check email/IdP and admin panel access
5. **Communicate:** notify internal responders and affected partners/users as needed
6. **Harden:** document root cause and close policy/process gaps

## Web3-specific implementation notes

### Multisig signers and governance operators

- signer identities should use dedicated hardware and isolated accounts
- signer comms accounts (Telegram/Discord/X/email) must meet Tier 0/1 MFA policy
- treat signer-role changes as high-priority offboarding/onboarding events
- never co-locate signer seed phrase handling and MFA recovery artifacts on one device

### Exchange and custody accounts

- require hardware-backed MFA for withdrawal/admin roles
- enforce allowlists, withdrawal delays, and approval separation in addition to MFA
- monitor for MFA resets, new API keys, and withdrawal policy changes
- predefine emergency exchange freeze/escalation contacts

### Admin panels, deploy pipelines, and registrars

- enforce MFA on cloud consoles, DNS registrar, CI/CD, GitHub org owners, and incident tooling
- pair MFA with SSO/IdP conditional access where available
- alert on new factor enrollment and recovery events for privileged roles
- include these systems in quarterly access and factor reviews

## Minimum operating standard

At minimum, teams should enforce:

- MFA on every critical account
- hierarchy policy: **FIDO2/passkeys/security keys > TOTP > push > SMS**
- no SMS for critical accounts unless technically unavoidable and documented
- documented enrollment, offboarding, recovery, and break-glass procedures
- quarterly ownership and factor review
- incident playbook for suspected MFA compromise, tested via drills

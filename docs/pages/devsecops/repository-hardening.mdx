# Repository Hardening

<TagList tags={frontmatter.tags} />
<AttributionList contributors={frontmatter.contributors} />

If a threat actor gains write access to your repository, they can tamper with code, CI, and release pipelines. Treat
repository settings as high-impact security controls.

## Recommended controls

1. Require MFA for all organization members and outside collaborators.
2. Protect critical branches with rulesets (status checks, required reviews, signed commits, and restricted pushes).
3. Restrict who can edit workflow files and CI secrets.
4. Enable secret scanning and push protection.
5. Enforce least-privilege repository roles and review access regularly.
6. Require signed commits/tags for critical branches and release workflows.
7. Continuously monitor dependency and supply-chain risk.

## Practical examples

### Example 1: Enforce branch rules for release branches

For `main`, `develop`, and release branches:

- Require pull requests and disallow force pushes.
- Require status checks (tests, linting, security scans).
- Require code owner reviews for high-risk paths (for example `.github/workflows/`, `docs/pages/config/`).

### Example 2: Enable push protection for secrets

Turn on secret scanning push protection so contributors are blocked before committing known key patterns.

### Example 3: Lock down Actions and reusable workflows

- Only allow trusted actions (GitHub-owned, verified creators, and allowlisted local actions).
- Require approval for first-time contributors before workflow execution.
- Store cloud credentials in protected environments, not repository-level broad secrets.

### Example 4: Review high-risk settings monthly

Use a recurring checklist to verify:

- branch/ruleset protections,
- repository admin list,
- Actions permissions,
- required reviewers for production environments,
- audit log anomalies.

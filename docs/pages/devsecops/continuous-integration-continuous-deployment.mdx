# Continuous Integration and Continuous Deployment (CI/CD)

<TagList tags={frontmatter.tags} />
<AttributionList contributors={frontmatter.contributors} />

CI/CD systems are part of your production attack surface. Secure pipelines should be reproducible, auditable, and
least-privileged by default.

## Recommended controls

1. Require CI checks on every pull request before merge.
2. Pin third-party GitHub Actions to full commit SHAs.
3. Use least-privilege `permissions` in workflow files.
4. Prefer short-lived cloud credentials via OIDC over long-lived static secrets.
5. Build in isolated runners/environments and avoid sharing mutable state between jobs.
6. Scan dependencies, IaC, and secrets as part of CI.

## Practical examples

### Example 1: Lock down workflow token permissions

```yaml
permissions:
  contents: read
```

Then elevate permissions only for jobs that truly need write access.

### Example 2: Pin all third-party actions

```yaml
- uses: actions/checkout@34e114876b0b11c390a56381ad16ebd13914f8d5 # v4.3.1
```

Pinning prevents silent supply-chain changes from mutable tags.

### Example 3: Replace cloud access keys with OIDC

In AWS, configure a role trusted by GitHub OIDC and assume it at runtime:

```yaml
- uses: aws-actions/configure-aws-credentials@v4
  with:
    role-to-assume: ${{ secrets.AWS_IAM_ROLE_TO_ASSUME }}
    aws-region: us-east-2
```

This removes persistent keys from repository secrets.

### Example 4: Add policy checks before deploy

Run tools like dependency review, SAST, secret scanning, and IaC checks in CI gates before deployment jobs execute.

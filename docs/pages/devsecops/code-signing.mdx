# Code Signing

<TagList tags={frontmatter.tags} />
<AttributionList contributors={frontmatter.contributors} />

Code signing helps prove authorship and integrity. It does not replace peer review, but it gives maintainers a strong
signal that code and release artifacts came from trusted contributors and trusted automation.

## Recommended controls

1. Require signed commits for all contributors (GPG, SSH, or S/MIME) and enforce it on protected branches.
2. Require at least one independent reviewer before merge.
3. Require MFA for all maintainers and prefer phishing-resistant hardware keys.
4. Rotate signing keys on a schedule and immediately after staff changes.
5. Keep a written key management playbook (creation, backup, revocation, rotation, offboarding).

## Practical examples

### Example 1: Enforce signed commits on `develop` and `main`

- In **Repository Settings → Branches/Rulesets**, require signed commits and pull-request reviews.
- Deny direct pushes to protected branches so unsigned emergency pushes are not possible.

### Example 2: Protect release artifacts with Sigstore

For binaries, container images, or build outputs, sign artifacts in CI and verify before publish.

```bash
cosign sign --yes ghcr.io/org/app:1.2.3
cosign verify ghcr.io/org/app:1.2.3 --certificate-identity-regexp 'https://github.com/org/repo/.*'
```

This provides provenance beyond commit-level signatures.

### Example 3: Fast key compromise response

If a maintainer key is suspected compromised:

1. Revoke the key immediately.
2. Remove the key from GitHub.
3. Rotate credentials and tokens tied to the same device/account.
4. Re-sign subsequent release tags/artifacts with a new trusted key.

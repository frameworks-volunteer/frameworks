# Secure Coding Standards and Guidelines

<TagList tags={frontmatter.tags} />
<AttributionList contributors={frontmatter.contributors} />

Secure coding standards reduce avoidable vulnerabilities and make security expectations explicit across teams. The goal is
not just to "write secure code" once, but to build repeatable engineering habits that prevent common mistakes in every
release.

## Core Secure Coding Standards

### 1) Input Validation

Validate all untrusted input at system boundaries (API handlers, job consumers, file parsers). Favor allowlists and
explicit schemas over ad-hoc checks.

**Practical example (TypeScript + API):**

```ts
import { z } from 'zod'

const CreateUserSchema = z.object({
  email: z.string().email().max(254),
  age: z.number().int().min(13).max(120),
  role: z.enum(['viewer', 'editor'])
})

export async function createUser(req, res) {
  const parsed = CreateUserSchema.safeParse(req.body)
  if (!parsed.success) {
    return res.status(400).json({ error: 'Invalid request payload' })
  }

  // Use parameterized queries/ORM, never string concatenation
  await db.user.create({ data: parsed.data })
  return res.status(201).json({ ok: true })
}
```

**Implementation notes:**

- Reject malformed data early with 4xx responses.
- Normalize canonical formats where needed (e.g., lowercase email).
- Use parameterized queries to prevent SQL injection.

### 2) Output Encoding (Context-Aware)

Encode or escape output based on where it is rendered (HTML, URL, JS string, CSS). Incorrect context handling can lead
to XSS even when validation exists.

**Practical example:**

- Prefer frameworks that auto-escape by default.
- Avoid unsafe rendering APIs (`dangerouslySetInnerHTML`, raw template interpolation) unless content is sanitized with a
  vetted sanitizer.

```tsx
// Safer default in React: rendered as text, escaped by default
<div>{userSuppliedComment}</div>

// Risky pattern: only use with strong sanitization controls
<div dangerouslySetInnerHTML={{ __html: sanitizedHtml }} />
```

### 3) Authentication and Authorization

Treat authentication (who are you?) and authorization (what can you do?) as separate controls. Enforce server-side
authorization for every sensitive action.

**Practical example (object-level authorization):**

```ts
export async function updateInvoice(req, res) {
  const user = req.authnUser // established by auth middleware
  const invoice = await db.invoice.findUnique({ where: { id: req.params.id } })

  if (!invoice) return res.status(404).json({ error: 'Not found' })
  if (invoice.ownerId !== user.id && !user.roles.includes('admin')) {
    return res.status(403).json({ error: 'Forbidden' })
  }

  await db.invoice.update({ where: { id: invoice.id }, data: req.body })
  return res.status(200).json({ ok: true })
}
```

**Implementation notes:**

- Deny by default; grant minimal permissions.
- Re-check authorization in backend services even if the frontend hides actions.
- Protect session/token handling and enforce MFA for privileged access.

### 4) Error Handling and Secure Logging

Errors should help operators debug without leaking secrets, stack internals, tokens, or PII to end users.

**Practical example:**

```ts
try {
  await paymentService.charge(cardToken, amount)
  return res.status(200).json({ ok: true })
} catch (err) {
  logger.error({ reqId: req.id, errType: err.name }, 'Payment failed')
  return res.status(502).json({ error: 'Unable to process payment right now' })
}
```

**Implementation notes:**

- Return generic user-facing errors.
- Log structured metadata with correlation/request IDs.
- Redact secrets in logs and telemetry.

## Secure Coding Implementation Guidelines

### 1) Use Vetted Libraries and Keep Dependencies Healthy

- Prefer actively maintained libraries with clear security posture.
- Pin or constrain versions and apply updates regularly.
- Automate dependency scanning in CI (SCA + advisory feeds).

**Practical workflow:**

- Weekly dependency update window.
- CI fails on critical vulnerabilities unless a documented exception exists.
- Track exceptions with owner + expiry date.

### 2) Follow Least Privilege by Default

- Services, jobs, and CI pipelines should run with the minimum permissions required.
- Avoid broad database, cloud IAM, and filesystem permissions.

**Practical workflow:**

- Separate read-only and write-capable service accounts.
- Remove default admin permissions from non-admin roles.
- Review privilege grants during release and incident retrospectives.

### 3) Protect Secrets and Sensitive Data

- Never hardcode secrets in source code.
- Use dedicated secret managers and short-lived credentials where possible.
- Encrypt sensitive data in transit and at rest.

**Practical workflow:**

- Secret scanning in pre-commit and CI.
- Key rotation policy with automated reminders.
- Data classification to distinguish public, internal, confidential, and regulated data.

### 4) Make Security Reviews Part of Definition of Done

- Use security checklists in code review templates.
- Pair manual review with SAST/DAST and test coverage for abuse cases.

**Practical workflow:**

- Pull requests require: threat notes, test evidence, and no unresolved high-severity findings.
- Security-relevant changes (auth, crypto, deserialization, file upload) require an explicit reviewer.

### 5) Invest in Continuous Security Training

- Provide regular secure coding refreshers tied to real incidents and near-misses.
- Build a security champion model per squad/team.

**Practical workflow:**

- Monthly micro-training using one vulnerability class (e.g., IDOR, SSRF).
- Post-incident learning notes mapped back to coding standards.

## Lightweight Secure Coding Checklist

Use this checklist before merging security-relevant code:

- [ ] Input schema validation exists for all untrusted entry points.
- [ ] Authorization checks are server-side and deny by default.
- [ ] Output encoding/sanitization matches rendering context.
- [ ] Errors do not leak secrets or sensitive internals.
- [ ] Secrets are not in code, logs, or client-side artifacts.
- [ ] Dependencies were scanned and critical findings addressed.
